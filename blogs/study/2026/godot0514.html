# 星露谷物语模块化设计全景解析

# 前言

上篇 godot0513.md 讲了角色像素画的模块拆分（Body / Feet / Hands），但星露谷的模块化远不止于此。翻阅游戏 .xnb 数据文件会发现，从物品到地图到 NPC 行为，整个游戏几乎全是"组合式"搭建的。这篇文章从数据、资源、行为三个维度拆解星露谷的模块化设计哲学。

# 一、数据驱动：一切皆表格

星露谷几乎所有游戏内容都由数据表（.xnb 反序列化后的对象数组）定义，不写死任何数值。

# 物品系统

Data/ObjectInformation.xnb 中每条记录定义：

ID / Name / Price / Edibility / Type / Category / Description
1

新增一个物品 = 加一行数据。工具、武器、种子、烹饪、鱼全走同一张表。

# 作物系统

Data/Crops.xnb 定义：

SeedID / GrowthStages[6] / HarvestID / RegrowDays / Seasons
1

每种作物拆成 6 个生长阶段 sprite，引擎按天数自动推进。跨季节种什么、是否复生、产出什么都是参数配置。

# 鱼系统

Data/Fish.xnb 每条鱼定义：

ID / Difficulty / BehaviorType / MinSize / MaxSize / Seasons / Time
1

钓鱼小游戏的物理行为统一，但浮标摆动速度、跳跃倾向、偏好深度全由数据参数差异化。一条鱼一个"类"，但根本没有类继承，全是参数差异。

# NPC 数据

Data/NPCDispositions.xnb 定义性格参数，Data/NPCGiftTastes.xnb 定义喜恶表，NPC 之间不写任何特殊代码。

  • NPC 日程 → Characters/Dialogue/*.xnb + Characters/schedules/*.xnb
  • 每个 NPC 的日程是独立的文本脚本，按天/季节/天气条件分支
  • 新增角色 = 新增数据行 + 日程文件，不需要触碰游戏主逻辑

# 小结

传统做法：  class WheatSeed extends Crop { ... }
星露谷做法：Crops.csv → { SeedID: 472, Stages: [1,2,2,3,3,4], Harvest: 284, ... }
1
2

改 Mod 不用改代码，改 CSV 就行。

# 二、资源模块化：一切皆独立文件

# XNB 原子化

每个独立视觉元素都有自己的 .xnb：

Characters/Farmer/farmer_base.xnb       → 基础身体
Characters/Farmer/farmer_shirts.xnb     → 上衣
Characters/Farmer/farmer_pants.xnb      → 裤子
Characters/Farmer/farmer_hats.xnb       → 帽子
Characters/Farmer/farmer_accessories.xnb → 配饰
Maps/spring_outdoorTileSheet.xnb        → 春季户外图块
Maps/fall_outdoorTileSheet.xnb          → 秋季户外图块
TerrainFeatures/seasonalCrop.xnb        → 季节性作物

# 地图 Tile 拼接

每张地图（农场、小镇、矿井等）是独立 .tbin 文件，由 tile 索引矩阵 + 图块集引用组成。不是整张大图。

地图 = terrain（地形层） + buildings（建筑层） + paths（路径层） + front（前景层）
1

每层可独立修改。Mod 作者替换地图文件就能重做整个场景布局。

# 三、行为模块化：一切皆脚本

# NPC 日程脚本

NPC 一天的动作用类似 DSL 的脚本描述：

630 BusStop 2 3 2
900 SeedShop 4 17 1
1200 Town 16 18 2 "rainy"
1400 Farm 100 200 3
1
2
3
4
  • 时间 地图 X Y 面向 + 可选条件
  • 支持天气/季节/日期条件分支
  • 引擎仅提供一个"逐条解析执行"的调度器，行为逻辑完全由数据驱动

# 事件系统

过场事件用纯文本指令：

addPete 64 16 2   → 在(64,16)添加Pete，面向下
move 2000 68 16 0 → 用2000ms移动到(68,16)，面向右
speak "你好！"     → 显示对话
1
2
3

社区 Mod 可以通过 Content Patcher 注入新事件，不需要修改游戏二进制。

# 动物行为

动物（鸡、牛、羊等）共用一套 AI：

  • 每天早上检查是否有建筑物 → 如果有则产出 → 检查好感度决定产品质量
  • 动物之间无差异代码，不同动物只通过 Data/animals.xnb 表定义：产出物、售价、生长时间、食量

# 四、这种设计带来的实际好处

维度 模块化前 模块化后
新增物品 建新类，写逻辑，注册到系统 加一行CSV
新增NPC 建新类，实现接口，处理AI 加数据 + 日程文件
换装 重绘所有帧 替换单个资源文件
改地图 改代码中的坐标硬编码 改 tbin 文件
做Mod 需要反向工程并hook代码 直接替换 xnb / tbin
季节扩展 加 if/else 分支 加一套精灵表

# 五、与角色模块化统一的底层思想

回看角色 Body / Feet / Hands 拆分，和上述设计是同一套哲学：

组合优于继承     → 角色 = body + feet + hands，Wheat = stage1 + stage2 + ...
数据驱动行为     → NPC性格、鱼的行为、作物生长全是参数，不是代码
资源文件原子化   → 每个独立视觉元素一个文件，可单独替换
1
2
3

ConcernedApe 虽一人开发，但用这套组合式架构把复杂度控制在了可管理的范围内，并且无意中为 Mod 社区留下了极其友好的扩展接口。

# 六、给游戏开发者的启发

  1. 能用数据表解决的，就不要写代码 — 物品、NPC、作物、任务，先放到表格里
  2. 资源文件粒度要细 — 别把所有角色塞一张大图，一个角色/一件物品一个文件，Mod 友好度天差地别
  3. 行为参数化，而不是硬编码子类 — 鱼的行为只需要 BehaviorType + 几个参数，不需要 FishFloppy / FishAggressive / FishBoss 一堆类
  4. 留好调度器，去掉逻辑 — NPC 日程框架只做调度不做决策，所有决策交给数据脚本

参考： 本文基于对 Stardew Valley 游戏解包数据分析（.xnb → JSON 反序列化）及 Content Patcher Mod 接口文档总结。
