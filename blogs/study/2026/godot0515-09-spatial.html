# 空间索引：大世界碰撞检测的根基

# 问题：N² 复杂度

一个 1000 个实体的游戏，每帧做碰撞检测：

foreach (var a in entities) {
    foreach (var b in entities) {
        if (a != b && Distance(a, b) < threshold) {
            OnCollision(a, b);
        }
    }
}

  • 100 个实体 → 10,000 次距离计算 → ✅ 没问题
  • 1000 个实体 → 1,000,000 次 → ⚠️ 开始卡
  • 10000 个实体 → 100,000,000 次 → ❌ 彻底崩

实际上大多数实体距离很远，根本不可能碰撞。99% 的比对是浪费的。

# 空间索引的核心思想

把空间分割成"格子"或"树"，只检查相邻区域内的实体。

无索引：          有索引：
A ↔ B ↔ C        [格1] A B    [格2] C D
  ↕   ↕           只检查 A↔B   只检查 C↔D
  D ↔ E          [格3] E      [格4]
                 A 和 E 距离远，不检查

# 方案一：空间哈希（Spatial Hash）—— 2D 世界的最优解

# 原理

把世界分成固定大小的网格（比如 64×64 像素），每个格子存一份实体列表。

class SpatialHash {
    float cellSize;  // 格子大小（通常 = 最大实体的直径）
    Dictionary<(int, int), List<Entity>> grid = new();

    public void Clear() => grid.Clear();

    public void Insert(Entity e) {
        var cells = GetOverlappingCells(e.Bounds);
        foreach (var cell in cells) {
            if (!grid.ContainsKey(cell))
                grid[cell] = new List<Entity>();
            grid[cell].Add(e);
        }
    }

    public List<Entity> Query(Vector3 position, float radius) {
        var result = new HashSet<Entity>();
        var cells = GetOverlappingCells(new Bounds(position, radius));
        foreach (var cell in cells) {
            if (grid.TryGetValue(cell, out var entities)) {
                foreach (var e in entities) {
                    if (Distance(e.position, position) < radius)
                        result.Add(e);
                }
            }
        }
        return result.ToList();
    }

    private List<(int, int)> GetOverlappingCells(Bounds bounds) {
        // 计算实体覆盖了哪些格子
        int minX = Mathf.FloorToInt(bounds.min.x / cellSize);
        int maxX = Mathf.FloorToInt(bounds.max.x / cellSize);
        int minY = Mathf.FloorToInt(bounds.min.y / cellSize);
        int maxY = Mathf.FloorToInt(bounds.max.y / cellSize);
        // 返回所有被覆盖的格子坐标
    }
}

# 使用

var hash = new SpatialHash(cellSize: 64);

void Update() {
    hash.Clear();
    foreach (var e in entities) hash.Insert(e);  // 每帧重建

    foreach (var e in entities) {
        var neighbors = hash.Query(e.position, e.radius);
        foreach (var n in neighbors) {
            if (e != n) ResolveCollision(e, n);
        }
    }
}

# 复杂度分析

方案 每帧时间
暴力 N² O(N²)
空间哈希 O(N × avgDensity)

avgDensity = 每个格子平均实体数量。如果格子大小合适（≈ 实体尺寸的 2 倍），avgDensity 通常 < 10。

10000 个实体：

  • 暴力：100,000,000 次比较
  • 空间哈希：10000 × 10 = 100,000 次比较 → 1000 倍加速

# 适用场景

场景 推荐 原因
2D 射击 / 割草 ✅ 空间哈希 实体分布均匀，格子大小好选
3D 大世界 ❌ 格子太多，内存爆炸
静态几何体 ❌ 用更专业的结构

# 方案二：四叉树 / 八叉树（Quadtree / Octree）

# 原理

不是固定网格，而是自适应分割：

         ┌─────┬─────┐
         │  A  │     │
         ├─────┤  B  │
         │  C  │     │
         ├─────┴─────┤
         │     D     │
         └───────────┘
1

4

7
  • 一个节点包含 > N 个实体 → 分裂成 4（2D）或 8（3D）个子节点
  • 实体少的区域不再细分
  • 实体密集的区域细分得更精细
class Quadtree {
    Bounds bounds;
    int capacity = 4;             // 每个节点最多放4个
    List<Entity> entities;
    Quadtree[] children;          // 4个子节点（NW, NE, SW, SE）

    public void Insert(Entity e) {
        if (!bounds.Contains(e.position)) return;

        if (children != null) {
            // 有子节点 → 交给对应子节点
            foreach (var child in children)
                child.Insert(e);
            return;
        }

        entities.Add(e);
        if (entities.Count > capacity) {
            Subdivide();  // 超出容量 → 分裂
            // 把现有实体重新分配到子节点
        }
    }

    public List<Entity> Query(Bounds range) {
        var result = new List<Entity>();
        if (!bounds.Intersects(range)) return result;

        foreach (var e in entities)
            if (range.Contains(e.position))
                result.Add(e);

        if (children != null)
            foreach (var child in children)
                result.AddRange(child.Query(range));

        return result;
    }
}

# 四叉树 vs 空间哈希

空间哈希 四叉树
实现复杂度 低 中
动态实体（每帧移动） 每帧重建 每帧更新位置
密度自适应 ❌ 固定格子 ✅ 密度高自动细分
性能下限 格子不合适时等同于遍历 最坏情况 ≈ 遍历
3D 扩展 直接扩展为 3D 网格 直接扩展为八叉树

# 实际案例

《帝国时代》 的地形选择系统：

  • 单位寻路时不需要扫描全图地图
  • 四叉树快速定位单位所在区域的通行状态
  • 选 100 个农民点时，四叉树把搜索从全图缩小到局部

# 方案三：BVH（包围盒层级树）

# 原理

BVH 不对空间做分割，而是对物体做分割：

                 [Root]
                /      \
          [A+C+E]      [B+D+F]
         /       \     /       \
       [A+C]    [E]  [B+F]    [D]
       /    \        /    \
      [A]  [C]     [B]  [F]

  • 叶子节点 = 一个实体
  • 父节点 = 所有子节点的 AABB（轴对齐包围盒）的并集

# 应用：碰撞检测

bool CheckCollision(BVHNode node, Entity target) {
    if (!node.aabb.Intersects(target.aabb))
        return false;        // 整棵树都不碰撞 → 跳过所有子节点

    if (node.isLeaf)
        return node.entity.Intersects(target);

    return CheckCollision(node.left, target) ||
           CheckCollision(node.right, target);
}

# BVH vs 空间索引

空间哈希 / 四叉树 BVH
分割对象 分割空间 分割物体
动态更新 重建或移动实体 更新包围盒
用途 碰撞检测、寻路 渲染裁剪、光线追踪
适合 均匀分布 任意分布

# 实际案例

光线追踪（包括游戏中的实时光追）：

  • BVH 是光追的核心数据结构
  • NVIDIA RTX 硬件内置 BVH 遍历加速
  • 每条光线只需要遍历 BVH，不需要测试场景中所有三角形

# 方案选择指南

你的游戏类型？
├── 2D 射击 / 动作
│   ├── 实体密集（< 5000）→ 空间哈希（最简单）
│   └── 实体超多（> 5000）→ 四叉树
├── 2D / 3D 大世界
│   ├── 碰撞检测 → 空间哈希 + 四叉树混合

├── 3D FPS / TPS
│   ├── 渲染裁剪 → 八叉树 / BVH
│   └── 碰撞检测 → 空间哈希

# 实际项目建议

  1. 小游戏 (< 100 实体) — 不需要空间索引，N² 暴力检测更快（因为索引本身有开销）
  2. 2D 中型游戏 (100~5000) — 空间哈希，格子大小 = 最大实体尺寸 × 2
  3. 3D 开放世界 — 八叉树 + 空间哈希双管齐下
  4. 物理引擎 — 不要自己写，直接用 Box2D / PhysX / Bullet，它们内部实现了最优空间索引

# 性能验证

实际项目中，从暴力到空间索引的优化效果：

实体数        暴力(N²)      空间哈希        加速比
  100        10,000         ~500          20x
 1000       1,000,000      ~5,000        200x
10000     100,000,000      ~50,000      2000x

实体越多，空间索引的收益越大。 这就是为什么大世界游戏不能没有它。

一句话总结： 空间索引的核心是"只检查可能撞上的"，而非"检查所有"。空间哈希最简单，四叉树最均衡，BVH 最通用。没有空间索引的大世界游戏，帧率天花板会很矮。
