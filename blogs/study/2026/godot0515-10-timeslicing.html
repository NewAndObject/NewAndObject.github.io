# 子帧调度与 Job System：把 16.67ms 用到极致

# 问题：一帧做不完怎么办

一个 60fps 游戏，每帧只有 16.67ms 完成所有工作。

典型的帧时间分布：

|←────── 16.67ms (60fps) ──────→|
├──────────┬──────────┬──────────┤
│  逻辑更新  │  物理模拟  │   渲染    │
│  8ms      │  5ms     │  10ms    │ ← 单线程竟然够？不，还会更多...
├──────────┴──────────┴──────────┤
│  AI寻路  │ 粒子更新 │ 音效混音 │ 网络收发 │ GC ...
│  3ms     │  2ms    │  1ms     │  2ms    │ 5ms ← ❌ 超了！

单帧超 16.67ms → 掉帧。解决思路有两个：

  1. 多线程并行（Job System）— 同时做多件事
  2. 拆到多帧执行（Time Slicing）— 把大任务打散

# 一、Time Slicing：把大任务切成小片

# 问题场景

寻路 100 个单位：

void Update() {
    foreach (var unit in units) {
        unit.FindPath();  // 每个单位的寻路耗时 1~3ms
    }
    // 如果 100 个单位，这一帧直接卡几十毫秒
}

# 解决方案：每帧只做一部分

class PathfindingScheduler {
    List<Unit> units;
    int currentIndex = 0;
    int batchSize = 5;

    void Update() {
        int processed = 0;
        while (processed < batchSize && currentIndex < units.Count) {
            units[currentIndex].FindPath();
            currentIndex++;
            processed++;
        }

        if (currentIndex >= units.Count)
            currentIndex = 0;  // 一轮完成，下一帧从头开始
    }
}

# 更通用的实现

class TimeSlicedTask {
    IEnumerator routine;
    float timeBudgetMs;

    public bool Execute(float budgetMs) {
        float endTime = Time.realtimeSinceStartup + budgetMs / 1000f;
        while (Time.realtimeSinceStartup < endTime) {
            if (!routine.MoveNext()) return true;  // 完成
        }
        return false;  // 预算用完，下一帧继续
    }
}

// 使用
var task = new TimeSlicedTask(LoadLevelRoutine());

void Update() {
    if (!task.Execute(2.0f)) {  // 每帧最多用 2ms 加载
        // 还没加载完，显示进度条
    } else {
        // 加载完成，进入关卡
    }
}

# 适用场景

任务 是否适合 Time Slicing 原因
寻路 ✅ 晚几帧到达不影响体验
关卡加载 ✅ 本身就是异步的
AI 决策 ✅ 不需要每帧重新决策
物理模拟 ❌ 必须每帧完整模拟，否则穿模
玩家输入 ❌ 必须立即响应
渲染 ❌ 渲染必须每帧完整提交

# 二、Job System：多核并行

# 洞察

现代 CPU 有 4~16 个核心，但大多数游戏只用了一个：

# 手动实现（简化）

class JobSystem {
    Thread[] workers;
    Queue<Action> jobs = new();
    object lockObj = new();

    public JobSystem(int threadCount) {
        workers = new Thread[threadCount];
        for (int i = 0; i < threadCount; i++) {
            workers[i] = new Thread(WorkerLoop);
            workers[i].Start();
        }
    }

    public void Schedule(Action job) {
        lock (lockObj) jobs.Enqueue(job);
    }

    public void WaitAll() {
        // 等待所有 Job 完成
    }

    void WorkerLoop() {
        while (true) {
            Action job = null;
            lock (lockObj) {
                if (jobs.Count > 0) job = jobs.Dequeue();
            }
            job?.Invoke();
        }
    }
}

// 使用
var jobSystem = new JobSystem(4);  // 4个工作线程

void Update() {
    // 并行调度
    foreach (var ai in allAI) {
        jobSystem.Schedule(() => ai.Think());
    }
    foreach (var particle in allParticleSystems) {
        jobSystem.Schedule(() => particle.Update());
    }

    jobSystem.WaitAll();  // 等所有 Job 完成

    Render();  // 主线程渲染
}

实现方式：Job 句柄 + 依赖计数

class JobHandle {
    int pendingDependencies;

    public JobHandle(params JobHandle[] dependencies) {
        pendingDependencies = dependencies.Length;
        foreach (var dep in dependencies)
            dep.OnComplete += () => {
                if (--pendingDependencies == 0) Schedule();
            };
    }

    public bool IsComplete => pendingDependencies == 0;
}

# Unity 的 Job System（官方实现）

Unity 的 C# Job System 是生产级实现：

// 1. 定义 Job（值类型，无GC）
struct MoveJob : IJobParallelFor {
    public NativeArray<Vector3> positions;
    public NativeArray<Vector3> velocities;
    public float deltaTime;

    public void Execute(int i) {
        positions[i] += velocities[i] * deltaTime;
    }
}

// 2. 调度
var job = new MoveJob {
    positions = positionsArray,
    velocities = velocitiesArray,
    deltaTime = Time.deltaTime
};

JobHandle handle = job.Schedule(positionsArray.Length, 64);
// 第3个参数64 = batch size，64个元素一组分给一个线程

// 3. 等待
handle.Complete();

# 三、混合使用：Time Slicing + Job System

现代引擎两者同时使用：

每帧开始：
  ├── Time Slicing: 继续上一帧没做完的寻路（5个单位）
  ├── Job System: 并行计算AI（4线程）
  ├── Job System: 并行更新粒子（4线程）
  ├── Time Slicing: 流式加载地图区块
  └── 主线程：渲染

16.67ms 用满 → 60fps ✅

# 实际案例：《蜘蛛侠》PS4 的 Job System

Insomniac Games 分享的数据：

传统单线程：  50+ 个系统顺序执行 → 单帧 33ms → 30fps
Job System： 50+ 个系统并行 → 每帧平均16ms → 60fps
1
2

具体做法：

  • 100+ 个 Job 每帧
  • 6 个 worker 线程 + 1 个主线程
  • 依赖图自动调度
  • Hot Path 优先：与渲染相关的 Job 优先执行

# 实际案例：《城市：天际线》的 Time Slicing

每帧任务：
  1. 处理 50 个市民的 AI（市民总数 100,000+）
  2. 处理 10 栋建筑的交通计算
  3. 更新可见区域的渲染

总市民 100,000，每帧处理 50 个 → 每 2000 帧（约 33 秒）每个市民决策一次
玩家根本看不出 33 秒的决策延迟，但帧率稳住了。

# 四、实际项目建议

# Time Slicing 什么时候用

任务耗时 > 2ms，且不急于在一帧内完成 → Time Slicing
1

典型：寻路、加载、AI 长程规划、网络数据包处理。

# Job System 什么时候用

任务是并行的，且没有写冲突 → 丢进 Job System
1

典型：粒子更新、Transform 更新、动画求值、蒙皮。

# 坑

  1. 数据竞争 — 两个 Job 写同一块数据 → 崩溃。用只读共享 + 写入私有副本。
  2. 线程数不是越多越好 — 8 线程跑纯 CPU 任务时，线程切换开销可能超过并行收益。
  3. Amdahl 定律 — 如果任务有 30% 必须在主线程执行，那最多加速 1/(0.3) = 3.3 倍，不管多少核。

一句话总结： Time Slicing 把大任务拆到多帧，解决"一帧干不完"的问题；Job System 把任务分到多核，解决"一核干到冒烟、其他核在喝茶"的问题。大世界游戏两个都得有。
